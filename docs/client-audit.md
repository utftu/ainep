# Фактический прогон Claude Code

Дата: 2026-11-01. Версия: Claude Code 2.1.281, native macOS arm64.

SHA-256: `a922981f6f3b55a251ef9f9dbaa0621a5f99cbcb5ca67f8a797476ccfc83f626`.

Обезличенные наблюдения: [client-audit.json](client-audit.json). Исполняемый стенд: [audit.ts](../src/audit/audit.ts).

## Условия

Настоящий клиент запущен с искусственным API-ключом, временным пустым конфигом и локальным mock API. Доступ к сети ограничен sandbox-exec единственным localhost-портом наблюдателя. Дочерние процессы наследуют профиль. Пользовательские каталоги и известные Keychain Mach-сервисы запрещены, запись разрешена только в рабочую папку стенда и /dev/null. Фактическая проверка разрешённого порта, запрещённого второго порта и запрещённого искусственного файла прошла до запуска клиента. Проверка доступа к настоящему Keychain намеренно не выполнялась.

Это не полная виртуализация: системные файлы и сервисы macOS в общем случае доступны. Основные прогоны используют --bare, сравнительный — --safe-mode; телеметрия отключена во всех случаях. Полный обычный пользовательский запуск с настройками, плагинами и OAuth не моделировался. Трафик заблокированных попыток не записывался, поэтому полного перечня потенциальных внешних назначений этот отчёт не даёт.

## Результаты

| Сценарий | Результат | Что подтверждено |
|---|---|---|
| bare-message | Успех | Клиент принимает искусственный SSE-ответ |
| bare-read-tool | Успех | Получает tool_use Read, читает fixture.txt, передаёт содержимое в tool_result и завершает ответ |
| bare-resume | Успех | Продолжает ту же сессию; результат чтения присутствует в контексте |
| isolated-standard | Успех | Запрос с обычным системным промптом в safe-mode проходит тот же mock-цикл |
| proxied-read-tool | Успех | Цикл Read работает через proxy/privacy; metadata и клиентские ключ/заголовок сессии не достигают mock upstream |
| proxied-resume | Успех | Продолжение сессии работает через proxy/privacy с очищенным запросом |

Успех проверяется по результату клиента и наблюдаемым запросам. Для Read дополнительно проверяется уникальный маркер из тестового файла в успешном tool_result, а не только наличие блока такого типа.

## Реальная структура запросов этой версии

Во всех проверенных запусках наблюдались `/api/hello` и `/v1/messages?beta=true`. Ошибка от mock на `/api/hello` не помешала завершению сценариев. Через proxy этот маршрут также не перенаправляется. `/v1/messages/count_tokens` в этих сценариях не наблюдался.

В Messages-запросах присутствовали поля:

`model`, `messages`, `system`, `tools`, `metadata`, `max_tokens`, `thinking`, `context_management`, `stream`.

Тело передавалось без сжатия (`identity`), `stream` был true. Это наблюдение для локального custom base URL и выбранных режимов; оно не доказывает отсутствие gzip при подключении к first-party API.

Структура metadata подтверждена динамически:

```text
metadata: object
  user_id: string containing JSON
    device_id: string, length 64
    account_uuid: string, length 0
    session_id: string, length 36
```

Пустой account_uuid соответствует этому запуску с искусственным API-ключом без входа в аккаунт. Формат значения при OAuth не проверялся.

В заголовках реального клиента наблюдались `x-api-key`, `x-claude-code-session-id`, `x-app`, `x-stainless-os`, `x-stainless-arch`, `x-stainless-runtime`, `x-stainless-runtime-version`, `x-stainless-package-version`, `x-stainless-retry-count`, `x-stainless-timeout`, а также version/beta и обычные транспортные заголовки. Полные списки имён записаны в JSON; значения не записывались.

При прогоне через proxy на upstream отсутствуют `metadata`, `x-api-key`, `x-claude-code-session-id` и `x-stainless-*`. В заголовках остаётся серверный Authorization, значение которого искусственное и в отчёт не попадает.

## Что это меняет в решениях

Раньше структура user_id была подтверждена только исходниками cc-gateway; теперь она наблюдалась у установленного клиента в режиме API-ключа. Выяснилось, что идентификатор сессии также передаётся отдельным HTTP-заголовком; текущий allowlist прокси его удаляет.

Удаление metadata не сломало клиентский цикл и локальное resume в этом стенде. Но mock принимает запрос по нашей реализации: это не доказательство того, что сервер Anthropic примет такой же запрос с Pro/Max OAuth, и не свидетельство снижения вероятности блокировки. Решение об удалении metadata для реального OAuth остаётся экспериментальным.

Патч бинарника для этих шести сценариев не понадобился. Это не закрывает вопрос контроля всех соединений и поведения полноценного OAuth-клиента.
