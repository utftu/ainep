## Вывод

cc-gateway действительно изменяет отдельные поля запросов, но не обеспечивает полноту очистки, изоляцию сетевого трафика или анонимность аккаунта. В текущем коде есть собственные риски утечки токена и нарушения TLS. Совместимость с установленным Claude Code уже нарушена как минимум на уровне пути телеметрии.

Снижение количества передаваемых метаданных можно проверить. Снижение вероятности блокировки по этим исходникам измерить нельзя: серверные признаки, решения и история аккаунта неизвестны.

## Как работает шлюз

1. Launcher задаёт `ANTHROPIC_BASE_URL`, клиентский `ANTHROPIC_API_KEY`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` и `CLAUDE_CODE_ATTRIBUTION_HEADER=false`.
2. Сервер проверяет клиентский токен и полностью читает тело запроса в память.
3. Для нескольких известных путей выполняется JSON-преобразование. Некоторые заголовки удаляются, User-Agent заменяется.
4. Шлюз вставляет общий OAuth access token в `x-api-key` и отправляет HTTPS-запрос.
5. Ответ передаётся потоком через `pipe`, включая SSE.
6. OAuth обновляется таймером, новые значения хранятся в памяти процесса.

Шлюз не является системным перехватчиком сети. Он видит только запросы, которые клиент направил на его адрес. Launcher сам по себе не устанавливает сетевых запретов.

Дополнительные проблемы эксплуатации: Docker healthcheck всегда использует HTTP, включая TLS-конфигурацию; launcher считает непустой ответ healthcheck успехом независимо от статуса; `/_verify` демонстрирует искусственный пример и не доказывает очистку реального трафика.

## Что остаётся видимым

- В metadata.user_id меняется только device_id. account_uuid и session_id сохраняются намеренно; это закреплено штатным тестом.
- Реальный OAuth-токен по-прежнему позволяет серверу определить аккаунт. Замена email внутри одного события не меняет владельца токена.
- Текст обычных сообщений, tool results, содержимое файлов и другие вложенные структуры не проходят полную обезличивающую обработку. Имя, путь или адрес могут находиться там.
- В событиях произвольно вложенные поля не очищаются рекурсивно. additional_metadata теряет только три поля верхнего уровня: baseUrl, base_url, gateway.
- Сервер видит исходящий адрес соединения шлюза либо его внешнего прокси. Локальное размещение само по себе не меняет внешний IP.
- Подмена версии в User-Agent не меняет реальные возможности, форму запросов, beta-заголовки и поведение клиента.
- Cookies, неизвестные заголовки и неизвестные endpoints по умолчанию проходят дальше.

В непосредственной близости от uCr найдена uyo: для subscriber возвращаются apiKey:null и authToken:oauthAccessToken. Поэтому комментарий cc-gateway «Anthropic использует x-api-key для обоих типов токена» не подтверждается поведением штатного клиента. Принимает ли сервер альтернативный заголовок, без реального запроса неизвестно; это риск совместимости, а не доказанная ошибка авторизации.

Нельзя делать вывод «каждая найденная строка означает утечку»: в бинарнике есть отключённые ветки, служебные схемы, код разных режимов и сторонние библиотеки. В частности, число совпадений event names не равно числу реально отправляемых событий.

## Документированное поведение

Официальная [страница использования данных](https://code.claude.com/docs/en/data-usage) подтверждает отдельное управление метриками и отчётами об ошибках. Она также уточняет, что CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC не отключает WebFetch domain check и имеет исключение для auto-install официального marketplace. Следовательно, эта переменная не является гарантией отсутствия всех дополнительных сетевых соединений. Условия актуальной документации могут отличаться от старой установленной версии.

Официальная [документация шлюзов](https://code.claude.com/docs/en/llm-gateway) описывает шлюз как место управления credentials, расходами и маршрутизацией. Это не обещание анонимности или защиты от блокировки.

## Предлагаемая отправная точка

Первым результатом проекта должен стать воспроизводимый стенд проверки приватности для конкретной версии клиента: искусственные credentials, пустая конфигурация, локальный mock API и контролируемый сетевой выход. Он должен фиксировать назначения и схему запросов без хранения секретов, показывать отличия режимов запуска и проверять отсутствие неожиданных соединений.

Для самого шлюза необходимы закреплённый upstream origin, корректная TLS-проверка, loopback по умолчанию, ограничения тела и времени запроса, безопасное хранение credentials и явная политика обработки неизвестных форматов. Автоматическая подмена ОС и рабочих путей не должна приниматься как безопасная для работы агента без проверки семантики.

Критерий успеха: известная версия клиента передаёт только явно согласованные данные, а тесты обнаруживают изменение протокола при обновлении. Критерий «Anthropic не забанит» технически непроверяем с этой стороны.
